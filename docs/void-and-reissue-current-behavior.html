Void & Reissue: what the automation does, and where it stops

A V&R 837 is a replacement transaction. Today the automation treats it as one only when the original provider invoice is already settled — and even then, only for the invoice, never for its fees. This is the current behavior, the expected behavior, and the difference between them, keyed to where the original invoice sits when the V&R arrives.

01 · Vocabulary

Objects in play

The first four are distinct objects that conversation routinely collapses into “the invoice”. Every term below is used strictly as defined here throughout the document.

Provider invoice
The financial document created from an incoming provider claim (837). The object that gets settled and paid.
Corresponding fees
Fee records generated from a provider invoice. They carry their own status (Pending / Pay / Settled) and their own payment eligibility.
Original invoice
The provider invoice referenced by the incoming V&R via NTE*ADD. The version being superseded.
Replacement invoice
The provider invoice carried by the incoming V&R 837. The version that should supersede the original.
Globo
The system the invoice is uploaded into, where it moves Pending → Pay → Settled, and where a void or refund is applied.
Missing GOP / Missing Claim UI
Pre-Globo intake queues in the user interface. An item here is not yet in Globo; a user creates a GOP and enters the required ID to move it forward.
Automatic Refund
The existing automated reversal the V&R automation performs on a settled provider invoice. It acts on the provider invoice only.
Manual intervention
Any action the Billing team performs by hand because the automation does not perform it.

02 · Trigger and identification

How the original invoice is found

Trigger: an incoming 837 that contains Void & Reissue information. The automation identifies the original invoice from the NTE*ADD segment.

// 837 segment
NTE*ADD*Rplcmnt fr Voided Clm 13630117~
  1. Extract the referenced claim value — 13630117.
  2. Search for the InvoiceID against which that value was registered.
  3. Use that InvoiceID to locate the original invoice.

The reference arrives on every V&R, independent of where the original invoice currently sits. What differs today is what the automation does with it once the original has been located.

Requires technical confirmation In Scenarios 3 and 4 the original is not neutralized. It is not established from the described behavior whether the NTE*ADD lookup (a) is not executed, (b) executes but fails to resolve for a non-settled or not-yet-uploaded original, or (c) resolves successfully but has no downstream action wired to it. The fix differs per case.

04 · Lifecycle

Where the V&R lands, and what it reaches

Same geometry in both figures: the original invoice's path across intake and Globo, and the fees that come off it. What changes is which arrows exist.

Reading the dispatch The branch is chosen by where the original is when the V&R arrives, not by anything in the replacement. Fee handling attaches to the settled branch, and then splits again on fee status: paid fees are refunded, Pending/Pay fees are voided.

05 · Detail

Current vs. expected, per scenario

S1

Provider invoice and corresponding fees already settled

value not recovered
Provider invoice: Settled Corresponding fees: Settled

Current behavior

  1. Automation reads the NTE*ADD segment.
  2. Automation identifies the original invoice.
  3. Automation performs Automatic Refund on the provider invoice.
  4. The replacement invoice can then be processed.
  5. The corresponding fees are not refunded.

Confirmed with the Billing team.

Expected behavior

When the original provider invoice is refunded because of a V&R, the corresponding fees generated from that invoice should also be automatically refunded/voided.

The original financial transaction and its associated fees are reversed together.

Manual todayThe Billing team must manually refund the fees associated with the original invoice.
S2

Provider invoice settled, fees created but not yet settled

duplicate payment possible
Provider invoice: Settled Corresponding fees: Pending or Pay

Current behavior

  1. Automation identifies the original provider invoice.
  2. Automation performs Automatic Refund on the provider invoice.
  3. The corresponding fees remain untouched in Pending or Pay status.

Fees relating to an invoice that has already been voided can remain eligible for payment.

Expected behavior

When the original provider invoice is voided/refunded, any corresponding fees still in Pending or Pay status should also be automatically voided.

Those fees are no longer valid — they belong to the superseded version of the provider invoice.

Manual todayThe Billing team must manually identify and void the fees created for the original invoice.
S3

Original provider invoice still Pending or Pay in Globo

duplicate payment possible
Provider invoice: Pending or Pay Location: already in Globo Settlement: not yet settled

Current behavior

  1. The automation does not treat the incoming invoice as a replacement of the existing invoice.
  2. The replacement appears in the UI under Missing GOP or Missing Claim, behaving as a new invoice.
  3. The user must create a new GOP in the case.
  4. The user enters the required ID in the UI.
  5. The replacement invoice is uploaded into Globo.
  6. Uploading the replacement does not void the original.

Both the original and the replacement invoice can exist in Globo simultaneously.

Expected behavior

  1. Automation identifies the original invoice through the V&R reference.
  2. Automation automatically voids the original invoice.
  3. Automation creates/uploads the replacement version.
  4. Only the replacement invoice remains valid for further processing/payment.

One live invoice per claim at all times.

Manual todayThe Billing team must manually void the original invoice to prevent duplicate payment.
S4

Original invoice has not yet reached Globo

duplicate payment possible
Provider invoice: not yet uploaded into Globo Location: Missing GOP and/or Missing Claim UI

Current behavior

  1. The replacement appears in the UI as another new invoice.
  2. There is no automated connection between the original UI item and the replacement V&R item.
  3. Both versions can therefore remain available for processing.

If the Billing team recognizes the new invoice as a V&R:

  • original still in Missing GOP / Missing Claim UI → the team manually removes the original item;
  • original already uploaded into Globo by then → the team must manually void it in Globo.

Expected behavior

The V&R reference should allow the system to identify that the incoming invoice supersedes an invoice already present in the intake process.

If the original is still in the Missing GOP / Missing Claim UI:

  1. The original is automatically cancelled/removed from processing.
  2. The replacement becomes the active version.

If the original has moved into Globo:

  1. The original is automatically voided.
  2. The replacement becomes the active version.

The system prevents both invoice versions from progressing independently.

Manual todayManual removal of the original UI item, or a manual void in Globo — and only when a human recognizes the incoming invoice as a V&R.

06 · For the developer

Gap summary

G1 Fee reversal is not chained to invoice reversal. Automatic Refund acts on the provider invoice only. S1: fees stay paid and unrecovered. S2: fees stay payable against a voided invoice. S1 · S2
G2 No void path for a non-settled original. A V&R against an original sitting in Globo at Pending/Pay does not void it, so two live invoices exist for the same claim. S3
G3 No linkage at intake. A V&R against an original still in Missing GOP / Missing Claim is not connected to that UI item; two independent items progress and nothing stops both reaching Globo. S4
G4 The reversal action is not selected by lifecycle state. The only wired outcome is Automatic Refund on a settled invoice; the other states have no outcome, so the NTE*ADD reference is effectively unused outside the settled case. S3 · S4

Root cause, stated once: the automation implements V&R as “refund a settled provider invoice”, not as “replace whatever version currently exists, wherever it currently sits.” There is no dispatch on the original's lifecycle state, and no propagation from the invoice reversal to its dependent fee records.

A V&R should behave as a replacement transaction, not as an independent new invoice. Once the replacement is identified through the NTE*ADD reference, the system should automatically neutralize the previous version wherever it currently sits in the workflow, including any associated fees where applicable.

07 · Target logic

Potential functional rule

Developer-oriented expression of the desired behavior. Pseudocode, not an implementation contract.

IF incoming 837 is identified as V&R

  → locate original invoice using NTE*ADD reference
        extract claim ref → resolve InvoiceID → locate original invoice

  → determine current lifecycle state of original

  → neutralize original invoice appropriately
        state = Missing GOP / Missing Claim UI  → cancel / remove item from processing
        state = Globo, Pending or Pay           → void original invoice
        state = Globo, Settled                  → Automatic Refund on provider invoice

  → neutralize associated fees where applicable
        fees  = Settled                         → refund / void fees
        fees  = Pending or Pay                  → void fees

  → process replacement as the only active version

  → prevent duplicate payment exposure
        original and replacement must never both be eligible for payment

08 · Before requirements are frozen

Requires technical confirmation

These are not described behavior. Nothing here should be written into requirements until it is answered.

  1. Whether the NTE*ADD lookup runs, resolves, or is simply not acted on for non-settled and not-yet-uploaded originals.
  2. At which lifecycle point corresponding fees are generated from a provider invoice. S2 confirms fees can exist while unsettled; the creation trigger itself is not described.
  3. Whether “refund” and “void” on fees are distinct operations in the fee model, or one operation whose effect depends on fee status.
  4. Whether Missing GOP and Missing Claim are one item or two separate items for the same invoice — and therefore whether cancellation must target both.
  5. Behavior when the NTE*ADD reference resolves to no invoice, to more than one invoice, or to an invoice already voided by an earlier V&R (chained V&R).
  6. Whether the replacement must be blocked from processing if neutralizing the original fails partway through — i.e. whether the sequence needs to be atomic.
